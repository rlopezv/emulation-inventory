# Fuentes de DAT

Catálogo pseudo-relacional de fuentes de DAT — no qué sistema usa cada una (eso es `docs/romsets.md`), sino **cómo se obtiene realmente cada fuente**, pensado como base para automatizar en el futuro su adquisición (detectar versión nueva, descargar, localizar el fichero correcto).

Tres tablas relacionadas por `id`:

1. **Fuentes** — la fuente en sí: de dónde se obtiene y por qué mecanismo.
2. **Contenido** — cada paquete de datos distinto que entrega una fuente (una fuente puede entregar varios: formato, alcance).
3. **Estructura** — solo para paquetes con layout interno no trivial: cada elemento (carpeta/patrón de fichero) como fila propia.

Ver también:

- `docs/romsets.md` — qué fuente usa cada sistema.
- `docs/tools.md` — herramientas de PC para gestionar/convertir/validar los DAT una vez obtenidos.
- `docs/guides/tools/dat-generation.md` — guía operativa (comandos exactos) de varias de estas fuentes.

## 3. Estructura

Solo para paquetes cuyo layout interno hay que localizar con un patrón — no aplica a los que son un único fichero directo.

En el YAML de `tools/application/dat_sources` (no en esta tabla, que se queda en 4 columnas) cada elemento admite además varios campos opcionales, documentados aquí en prosa dentro de `rol` cuando aplican — ver `tools/application/README.md` para el detalle completo del esquema:

- **`formato`** — solo cuando el `Formato` del Contenido padre no describe ya ese elemento (típicamente dentro de un `Mixto`, donde cada fichero suelto es de un formato distinto — ya sea otro formato de dato DAT, como en `libretro-mame`, o un formato auxiliar de fichero, como en `fresh1g1r-config`). Valores reconocidos: cualquiera del enum `Formato` normal (`xml-logiqx`, `clrmamepro-texto`...) o de los auxiliares `yaml-config`/`python` — ver `CLAUDE.md`.
- **`convencion_nombres`** — cuando el elemento es un patrón "un fichero por sistema" (`patron_ruta`) o una carpeta "una subcarpeta por sistema" (`carpeta` con `hijos: subcarpeta`), indica qué convención de nombrado usa la fuente para poder cruzarlo más adelante con nuestros identificadores canónicos, en vez de enumerar cada sistema a mano. Valores reconocidos: `no-intro`, `redump`, `redump-slug`, `tosec`, `mame-softwarelist`, `hyperspin`. Reconocer el valor no implica tener ya la correspondencia real, pero las 6 anteriores ya tienen manifiesto propio y autocontenido en `tools/application/src/dat_sources/config/system_names/<convencion>.json` (no una referencia a `tools/scripts/`).
- **`convencion_core`**, **`tipo`**, **`hijos`**/**`contenido_subcarpeta`** — campos nuevos del esquema recursivo (ver `tools/application/README.md#decisiones-ya-tomadas-para-el-modelo-objetivo`): `hijos: subcarpeta` permite que una `carpeta` resuelva `convencion_nombres` contra el nombre de cada subcarpeta (no solo contra nombre de fichero como `patron_ruta`), heredando el sistema resuelto a todo lo que cuelgue de ella; `contenido_subcarpeta` describe qué hay dentro de cada subcarpeta ya resuelta; `tipo` (`dat`/`auxiliar`/`config`) separa qué ES semánticamente la hoja de su `formato` de serialización; `convencion_core` resuelve en paralelo a un catálogo de cores/builds arcade, no a un sistema (sin manifiesto todavía).
